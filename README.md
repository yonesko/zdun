> *«Сижу, жду твои порты...»*

**Zdun** — легковесная CLI-утилита для параллельного ожидания готовности зависимостей (readiness probes) перед запуском основной команды. Заменяет громоздкие bash-скрипты на базе `nc`, `curl` и циклов `while`, избавляя контейнеры от лишних зависимостей.

После успешной готовности всех сервисов `zdun` бесшовно замещает себя целевым процессом через `execvp`.

---

## Возможности

* **Параллельный опрос**: все зависимости опрашиваются одновременно в асинхронных потоках, а не последовательно (таймаут попытки — 2s, пауза — 1s).
* **TCP и Dual-Stack (IPv4 / IPv6)**:
  * Быстрая проверка сокетов без `nc` / `netcat` (поддерживается прямой ввод: `tcp://[<ipv6>]:<port>`).
  * При резолве имени хоста `zdun` пробует все возвращённые A/AAAA адреса: если один протокол недоступен, автоматически выполняется fallback на остальные.
  * Проверка баннера сервиса на подстроку (`contains`) или регулярное выражение (`matches`).
* **HTTP(S)-проверки**:
  * Проверка статуса ответа (`2xx`), встроенный TLS/HTTPS.
  * Валидация тела ответа: поиск подстроки (`contains <substring>`) или регулярного выражения (`matches <regex>`).
  * Поддержка IPv6 в URL (например, `http://[::1]:8000/health`), корректная обработка UTF-8.
* **Регулярные выражения (POSIX ERE)**: проверки `matches <regex>` следуют стандарту POSIX Extended Regular Expressions (библиотека `regex-tdfa`).
* **Гибкий общий таймаут (`-t, --timeout`)**: поддержка форматов `ms`, `s`, `m`, `h`, дробных чисел (`500ms`, `10s`, `1m`, `2m30s`, `1h`, `0.5s`). По умолчанию `0` (ждать бесконечно).
* **Понятная диагностика**:
  * С флагом `-v, --verbose` — лог в реальном времени с локальными метками времени (`[zdun] [HH:MM:SS]`).
  * При сбое или таймауте — список всех непрошедших проверок с точными причинами последних ошибок в `stderr`.
* **Бесшовная передача управления**: целевой процесс запускается через `execvp` без лишних уровней в дереве процессов и накладных расходов памяти.

## Использование

```bash
zdun [ОПЦИИ] -- КОМАНДА [АРГУМЕНТЫ...]
```

> [!NOTE]
> Разделитель `--` обязателен и отделяет флаги `zdun` от запускаемой команды и её аргументов.

### Ключи:

* `-p, --probe PROBE` — спецификация проверки готовности (можно указывать несколько раз):
  * `tcp://<host>:<port>` — доступность TCP-порта (для IPv6: `tcp://[<ipv6>]:<port>`).
  * `"tcp://<host>:<port> contains <substring>"` — доступность порта и наличие подстроки в приветственном баннере сервера (SMTP, SSH, FTP и др.).
  * `"tcp://<host>:<port> matches <regex>"` — доступность порта и совпадение баннера с регулярным выражением (POSIX ERE).
  * `http://<url>` или `https://<url>` — успешный статус `2xx` (для IPv6: `http[s]://[<ipv6>]:<port>/...`).
  * `"http[s]://<url> contains <substring>"` — статус `2xx` и наличие подстроки в теле.
  * `"http[s]://<url> matches <regex>"` — статус `2xx` и совпадение тела с регулярным выражением (POSIX ERE).
* `-k, --insecure` — разрешить небезопасные соединения SSL/TLS (отключить проверку сертификатов для локальной разработки и тестовых стендов).
* `-t, --timeout DURATION` — общий таймаут ожидания всех сервисов (`10s`, `1m`, `2m30s`, `500ms`). По умолчанию `0` (ждать бесконечно).
* `-v, --verbose` — подробный лог выполнения проверок в `stderr` с таймштампами в реальном времени.
* `-h, --help` — показать справку.
* `--version` — показать версию.

## Коды возврата

`zdun` прозрачно транслирует код завершения целевой команды и использует стандартные коды POSIX при ошибках запуска:

| Код | Описание |
| :--- | :--- |
| **`0`** | Все проверки прошли успешно, и целевая команда завершилась с кодом `0`. |
| **`1`** | Ошибка аргументов либо истёк общий таймаут проверок (`--timeout`). |
| **`126`** | Команда найдена, но **не может быть запущена** (например, отсутствуют права `+x`). |
| **`127`** | Команда **не найдена** (бинарник отсутствует в `$PATH` или по указанному пути). |
| **`N`** | При успешном старте процесс `zdun` замещается целевым (`execvp`), поэтому возвращается фактический код завершения программы. |

## Примеры использования

### CLI

Параллельное ожидание базы данных, почтового сервера, мок-сервера и сервисов с проверкой ответов:

```bash
zdun \
  -p tcp://tsdb:5432 \
  -p "tcp://smtp:25 contains 220" \
  -p http://mock:8000/__admin/health \
  -p "http://kafka:9644/v1/status/ready contains ready" \
  -p "http://auth:8080/actuator/health contains UP" \
  -t 45s \
  -v \
  -- ./start-billing.sh
```

### Docker Compose

Параллельная проверка зависимостей сервиса перед стартом основного процесса:

```yaml
services:
  billing-service:
    image: my-app:latest
    depends_on:
      - tsdb
      - zookeeper
      - kafka
    command: >
      zdun
        -p tcp://tsdb:5432
        -p tcp://zookeeper:2181
        -p "http://kafka:9644/v1/status/ready contains ready"
        -t 60s
        -v
        -- ./start-billing.sh
```

### GitLab CI (`.gitlab-ci.yml`)

Параллельное ожидание сервисов в CI-пайплайне:

```yaml
test-billing:
  stage: test
  services:
    - name: tsdb:latest
      alias: tsdb
    - name: redpanda/redpanda:latest
      alias: kafka
    - name: wiremock/wiremock:latest
      alias: mock-server
    - name: temporalio/auto-setup:latest
      alias: temporal
  script:
    - zdun
        -p tcp://tsdb:5432
        -p "http://kafka:9644/v1/status/ready contains ready"
        -p http://mock-server:8000/__admin/health
        -p http://temporal:7243/api/v1/namespaces/default
        -t 45s
        -v
        -- ./gradlew test
```
