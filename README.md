> *«Сижу, жду твои порты...»*

**Zdun** — легковесная CLI-утилита для ожидания готовности зависимостей (readiness probes) перед запуском основной команды. Заменяет громоздкие bash-скрипты на базе `nc`, `curl` и циклов `while`.

Все проверки выполняются **параллельно**, с единым таймаутом и бесшовной передачей управления через `execvp`.

---

## Возможности

* **TCP-проверки (`tcp://host:port`)**: быстрая проверка доступности сокета без необходимости держать `nc` / `netcat` в образе.
* **HTTP(S)-проверки**:
  * Проверка успешного статуса ответа (`2xx`: `200 OK`, `201 Created`, `204 No Content` и др.).
  * Проверка тела ответа на наличие подстроки (`contains <substring>`).
  * Проверка тела ответа регулярным выражением (`matches <regex>`).
  * Встроенная поддержка TLS/HTTPS, корректная обработка кодировок (UTF-8).
* **Параллельное выполнение**: все зависимости опрашиваются одновременно в асинхронных потоках, а не последовательно.
* **Гибкий таймаут (`-t, --timeout`)**: поддержка форматов `ms`, `s`, `m`, `h`, дробных чисел (например: `500ms`, `10s`, `1m`, `2m30s`, `1h`, `0.5s`). По умолчанию `0` (ждать бесконечно).
* **Подробное логирование (`-v, --verbose`)**: поминутный лог с локальными метками времени (`[zdun] [HH:MM:SS]`) о старте, успехе или причинах сбоя каждой проверки.
* **Бесшовная передача управления**: после готовности всех сервисов запускает целевую команду через `execvp` — процесс утилиты замещается целевым процессом без накладных расходов памяти и лишних уровней в дереве процессов.

## Использование

```bash
zdun [ОПЦИИ] -- КОМАНДА [АРГУМЕНТЫ...]
```

> [!NOTE]
> Разделитель `--` обязателен и отделяет флаги `zdun` от запускаемой команды и её аргументов.

### Ключи:

* `-p, --probe PROBE` — спецификация проверки готовности (можно указывать несколько раз):
  * `tcp://<host>:<port>` — проверка доступности TCP-порта (для IPv6: `tcp://[<ipv6>]:<port>`).
  * `http://<url>` или `https://<url>` — проверка успешного статуса ответа (`2xx`).
  * `"http[s]://<url> contains <substring>"` — статус `2xx` и наличие подстроки в теле ответа.
  * `"http[s]://<url> matches <regex>"` — статус `2xx` и совпадение тела ответа с регулярным выражением.
* `-t, --timeout DURATION` — максимальное время ожидания всех сервисов (`10s`, `1m`, `2m30s`, `500ms`). По умолчанию `0` (ждать бесконечно).
* `-v, --verbose` — подробный лог выполнения проверок в `stderr` с таймштампами.
* `-h, --help` — показать справку.
* `--version` — показать версию.

## Коды возврата

`zdun` прозрачно транслирует код завершения целевой команды и использует стандартные коды POSIX при ошибках запуска:

| Код | Описание |
| :--- | :--- |
| **`0`** | Все проверки готовности прошли успешно, и целевая команда завершилась с кодом `0`. |
| **`1`** | Ошибка аргументов (например, не задана команда после `--`) либо истёк таймаут проверок (`--timeout`). |
| **`126`** | Команда найдена, но **не может быть запущена** (например, отсутствуют права на исполнение `+x`). |
| **`127`** | Команда **не найдена** (бинарник отсутствует в `$PATH` или по указанному пути). |
| **`N`** | При успешном старте процесс `zdun` замещается целевым (`execvp`), поэтому возвращается фактический код завершения запущенной программы. |

## Примеры использования

### CLI

Параллельное ожидание базы данных, мок-сервера и сервисов с проверкой содержимого ответов:

```bash
zdun \
  -p tcp://tsdb:5432 \
  -p http://mock:8000/__admin/health \
  -p "http://kafka:9644/v1/status/ready contains ready" \
  -p "http://auth:8080/actuator/health contains UP" \
  -t 45s \
  -v \
  -- ./start-billing.sh
```

### Docker Compose

Параллельная проверка зависимостей сервиса перед стартом основного процесса:

```yaml
services:
  billing-service:
    image: my-app:latest
    depends_on:
      - tsdb
      - zookeeper
      - kafka
    command: >
      zdun
        -p tcp://tsdb:5432
        -p tcp://zookeeper:2181
        -p "http://kafka:9644/v1/status/ready contains ready"
        -t 60s
        -v
        -- ./start-billing.sh
```

### GitLab CI (`.gitlab-ci.yml`)

Параллельное ожидание сервисов в CI-пайплайне:

```yaml
test-billing:
  stage: test
  services:
    - name: tsdb:latest
      alias: tsdb
    - name: redpanda/redpanda:latest
      alias: kafka
    - name: wiremock/wiremock:latest
      alias: mock-server
    - name: temporalio/auto-setup:latest
      alias: temporal
  script:
    - zdun
        -p tcp://tsdb:5432
        -p "http://kafka:9644/v1/status/ready contains ready"
        -p http://mock-server:8000/__admin/health
        -p http://temporal:7243/api/v1/namespaces/default
        -t 45s
        -v
        -- ./gradlew test
```

## Преимущества

1. **Скорость**: зависимости опрашиваются параллельно, а не последовательно. Если 5 сервисов стартуют за 10 секунд, `zdun` дождётся всех за 10 секунд вместо 50 секунд последовательных циклов `while`.
2. **Чистые образы**: в контейнере не нужны `curl`, `netcat`, `grep` или `bash` (идеально для Distroless / Scratch). Достаточно скопировать один статический бинарник `zdun`.
3. **Безопасный таймаут**: гарантированное завершение с ошибкой (`exit code 1`) вместо вечно зависшего CI-пайплайна.
4. **Понятная диагностика (`-v`)**: подробный лог выполнения с таймштампами и явными причинами ошибок:
   ```text
   [zdun] [09:30:12] Calling probe tcp://tsdb:5432
   [zdun] [09:30:12] Failed probe tcp://tsdb:5432: tsdb:5432: Connection refused
   [zdun] [09:30:13] Succeeded probe tcp://tsdb:5432
   [zdun] [09:30:13] All checks passed
   ```
   А при таймауте — список всех непрошедших проверок с деталями:
   ```text
   [zdun] [09:30:45] Some checks failed: tcp://tsdb:5432: done trying http://mock:8000/health: HTTP status 502
   ```
